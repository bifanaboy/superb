# UI Skills Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superb:subagent-driven-development (recommended) or superb:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add `ui-breaker` and `ui-design` skills that find and fix web UI problems with browser evidence.

**Architecture:** Two skills with shared reference files. `ui-breaker` is read-only and drives the browser tool the harness provides: the built-in `browser` namespace or the Playwright MCP. `ui-design` uses product-derived directions and asks `ui-breaker` to verify. Static HTML fixtures and a small Node server provide pressure-test targets.

**Tech Stack:** Markdown, Bash, Node 26, OpenCode `browser` namespace or Playwright MCP.

**Spec:** `docs/superb/specs/2026-10-31-ui-skills-design.md`

## Global Constraints

- `ui-breaker` changes no code. It writes only the report and blank credential keys in `.env`.
- The browser backend is the tool the harness provides: the built-in `browser` namespace on the desktop app, or a browser MCP such as the Playwright MCP on the TUI/CLI. No bundled script, no HTTP fetch as a substitute.
- With the built-in namespace, use `tools.browser.*` and keep the `tabID`. With the Playwright MCP, use `browser_navigate`, `browser_snapshot`, `browser_click` and the other `browser_*` tools; the tool list may prefix them with the server name. Discover the exact names first.
- `ui-breaker` never clicks a write action: no create, update, delete, send, or pay. Login submission is allowed. Sign-up, password reset and account changes are write actions.
- Credentials live in the project's `.env`. The file must be git-ignored. Add only missing blank keys. Set mode `600`. Use a test account. Never print the values.
- `ui-design` has no house style. Directions are product-derived. The taste references are calibration, not templates.
- Every new skill gets a failing pressure test first, per `writing-skills`.
- Descriptions start with "Use when..." and do not summarize the workflow. Keep each under 500 characters.
- Each `SKILL.md` stays under 500 words. Move detail to `references/`.
- The report uses the `audit` skill's three groups and four-part finding format, plus a `Type` line: `Flow`, `Craft`, or `Fit`.

## Review Focus

- A login-required app with no `.env`, or a tracked `.env`: the breaker must stop or ask, never write credentials to a tracked file.
- A write action that looks like navigation: the breaker must not click it, and the server log must show no write request.
- A page that is technically correct but wrong for its function: the breaker must report a `Fit` finding, not only `Craft`.
- A greenfield design request with no existing content: the design skill must derive a direction from the domain, audience and job, not from a style menu.
- A missing browser namespace or a page that fails to load: the breaker must stop and report the blocker, not claim it checked the UI.

- [ ] **Step 1: Write the failing fixture test**

Create `tests/opencode/test-ui-fixtures.mjs`:

```js
import fs from 'fs';
import path from 'path';

const root = path.resolve(import.meta.dirname, '..', 'ui', 'fixtures');
const read = (name) => {
  const file = path.join(root, name);
  if (!fs.existsSync(file)) throw new Error(`missing fixture: ${file}`);
  return fs.readFileSync(file, 'utf8');
};

const broken = read('broken.html');
const bland = read('bland.html');
const empty = read('empty.html');
const login = read('login.html');
const protectedPage = read('protected.html');

for (const marker of ['data-defect="flow"', 'data-defect="craft"', 'data-defect="fit"', 'data-write-action']) {
  if (!broken.includes(marker)) throw new Error(`broken.html missing ${marker}`);
}
if (!bland.includes('Inbox') || !bland.includes('Today')) throw new Error('bland.html missing task content');
if (!empty.includes('Ledger')) throw new Error('empty.html missing the product name');
if (!login.includes('name="user"') || !login.includes('name="pass"')) throw new Error('login.html missing form fields');
if (!protectedPage.includes('Protected dashboard')) throw new Error('protected.html missing marker');

console.log(JSON.stringify({ fixtures: ['broken', 'bland', 'empty', 'login', 'protected'] }));
```

- [ ] **Step 2: Run it to verify it fails**

Run: `node tests/opencode/test-ui-fixtures.mjs`
Expected: FAIL with `missing fixture: .../tests/ui/fixtures/broken.html`.

- [ ] **Step 3: Create the fixtures**

`broken.html` is a self-contained dashboard page. It must include:
- A marketing hero with an oversized italic serif headline and a logo wall, marked `data-defect="fit"`. The page is a task dashboard, so the hero does not fit the job.
- Three identical feature cards with icon tiles, marked `data-defect="fit"`.
- A low-contrast label, a cramped button, and a broken image `src="/missing.png"`, marked `data-defect="craft"`.
- A menu button that does nothing, and a search form that sends a GET and throws a console error on submit, marked `data-defect="flow"`.
- A `Delete account` button with `data-write-action` that calls `fetch('/delete', { method: 'POST' })`.
- A layout that overflows at 375px width.

`bland.html` is a functional task app with real content: `Inbox`, `Today`, `Upcoming`, a short task list, and a settings panel. It has plain styling and no marketing hero. It is the target for `ui-design`.

`empty.html` is a new product page with the name `Ledger`, one line of purpose, and an empty app shell. It is the greenfield target.

`login.html` is a form with `method="post"` and `action="/login"`, with `name="user"` and `name="pass"` fields and a submit button.

`protected.html` says `Protected dashboard` and lists one item.

- [ ] **Step 1: Write the failing static test**

Create `tests/opencode/test-ui-skills.mjs`:

```js
import fs from 'fs';
import path from 'path';

const root = path.resolve(import.meta.dirname, '..', '..');
const read = (rel) => fs.readFileSync(path.join(root, rel), 'utf8');
const skill = (name) => read(`skills/${name}/SKILL.md`);

const failures = [];
const check = (ok, message) => { if (!ok) failures.push(message); };

for (const name of ['ui-breaker', 'ui-design']) {
  const file = path.join(root, 'skills', name, 'SKILL.md');
  check(fs.existsSync(file), `missing ${file}`);
  if (!fs.existsSync(file)) continue;
  const text = skill(name);
  const match = text.match(/^---\nname:\s*(\S+)\ndescription:\s*(.+)\n---/);
  check(!!match, `${name}: invalid frontmatter`);
  if (match) {
    check(match[1] === name, `${name}: frontmatter name must be ${name}`);
    check(match[2].startsWith('Use when'), `${name}: description must start with "Use when"`);
    check(match[2].length <= 500, `${name}: description must be under 500 characters`);
  }
}

const breaker = skill('ui-breaker');
for (const phrase of ['write action', '.env', 'browser', 'Flow', 'Craft', 'Fit']) {
  check(breaker.includes(phrase), `ui-breaker: missing "${phrase}"`);
}
for (const ref of ['browser-protocol.md', 'report-format.md']) {
  check(fs.existsSync(path.join(root, 'skills/ui-breaker/references', ref)), `missing ui-breaker reference ${ref}`);
}
const protocolPath = path.join(root, 'skills/ui-breaker/references/browser-protocol.md');
if (fs.existsSync(protocolPath)) {
  const protocol = fs.readFileSync(protocolPath, 'utf8');
  for (const phrase of ['tabID', 'git check-ignore', '600', 'resize', 'lighthouse']) {
    check(protocol.includes(phrase), `browser-protocol: missing "${phrase}"`);
  }
}

const design = skill('ui-design');
for (const phrase of ['product-derived', 'no house style', 'DESIGN.md', 'ui-breaker']) {
  check(design.includes(phrase), `ui-design: missing "${phrase}"`);
}
for (const ref of ['taste-bar.md', 'direction-method.md', 'registers.md']) {
  check(fs.existsSync(path.join(root, 'skills/ui-design/references', ref)), `missing ui-design reference ${ref}`);
}

if (failures.length) {
  for (const failure of failures) console.error(`FAIL: ${failure}`);
  process.exit(1);
}
console.log(JSON.stringify({ skills: ['ui-breaker', 'ui-design'] }));
```

- [ ] **Step 3: Write `skills/ui-breaker/SKILL.md`**

Frontmatter: `name: ui-breaker`; a description that starts with "Use when" and names the triggers: the user sees a UI problem they cannot name, asks to test or review a web UI, or wants to know why a page looks or behaves wrong. Under 500 characters. Do not summarize the workflow.

Body, under 500 words:
- Overview: a critic with a playtester's hands. Read-only. Finds Flow, Craft and Fit problems with browser evidence.
- When to use and when not to use.
- Process: resolve the target; find the URL or start the app; check the branch; plan functional, adversarial and coverage rounds; run snapshot → act → snapshot → assert; write the report; ask issues or fix now.
- Credentials: link to the browser protocol; state the `.env` rules.
- Safety: no write actions; login is allowed; a read-only search is allowed; if unsure, do not act.
- Links: `references/browser-protocol.md`, `references/report-format.md`, and `../ui-design/references/taste-bar.md`.
- Limits: write flows, SSO/MFA, native apps, missing browser.
- Common rationalizations: "one screenshot is enough", "I'll click delete to test it", "the page loaded, so it works".

- [ ] **Step 4: Write `references/browser-protocol.md`**

Include:
- The backend: the built-in `browser` namespace on the desktop app, or the Playwright MCP on the TUI/CLI. Discover the exact tool names first.
- The loop: open, keep the `tabID`, snapshot, act, snapshot, assert. Pass the `tabID` to every call.
- The three planning rounds and the step budget.
- The evidence: `screenshot` on failures, `console`/`network`, `lighthouse` or a manual accessibility checklist, and `resize`/`setViewport` at 375px and 1440px.
- The `.env` credential flow, step by step, including the `git check-ignore` check, the additive blank keys, mode `600`, the test account warning, redaction, and the SSO/MFA stop.
- The no-write rule: create, update, delete, send, pay. Login is allowed. Sign-up, password reset and account changes are not.
- The branch check: the dev server must serve the branch under test, not main.
- The missing-tool stop.

- [ ] **Step 5: Write `references/report-format.md`**

Include:
- The start: surface register and design intent.
- The three groups: Must fix, Should fix, Nice to have.
- The four parts: what this is, problem, fix, if we skip it.
- The `Type` line: `Flow`, `Craft`, `Fit`.
- The ending: verdict, checked, not checked.
- The finding template.
- The rule that the report is the brief for `ui-design`.

- [ ] **Step 3: Write `references/taste-bar.md`**

- Content first. Space and type do the work.
- One narrow palette. One accent at most.
- Real imagery or none.
- Motion only when it explains a change.
- A voice that fits the product.
- No category template: no logo wall, no giant metrics, no identical card grid unless the content needs them.

- [ ] **Step 4: Write `references/direction-method.md`**

- Product facts: users, tasks, content, constraints, existing assets.
- Register selection.
- Concept discovery from the product's world.
- The one-line intent.
- Three distinct directions: name, idea, type, palette, layout logic, motion, what it sacrifices.
- Greenfield fallback: domain, audience, job.
- Local element fallback: the surrounding design system.
- Last resort: the style library, and state that you used it.
- The comparison page: static HTML/CSS, real content, three panels, mobile captures.
- The pick step.
- `DESIGN.md` schema: shared foundation plus a `surfaces` section, one entry per surface.

- [ ] **Step 5: Write `references/registers.md`**

Define Operate, Persuade, Read and Experience. For each: the visitor's success, the ambition level, examples, what to avoid. Include the rule that the register comes from the requested surface, not the product as a whole.
